# Deploying OptiCart to Render + MongoDB Atlas (free tier)

OptiCart is **two deployables** — a React/Vite client and an Express/TypeScript API —
plus **one database**. So you create **two Render services** and **one Atlas cluster**:

```
[ Render Static Site ]         [ Render Web Service ]        [ MongoDB Atlas M0 ]
  client (React/Vite)   ──▶      server (Express API)   ──▶     opticart database
  opticart-client...             opticart-api...
```

---

## ⚠️ Required code change (already applied)

The refresh-token cookie lives in `server/src/controllers/auth.ts` (`getCookieOptions`).
Because the client and API run on **different `onrender.com` subdomains**, the browser
treats requests between them as **cross-site**, and a `SameSite=Strict` cookie is **not
sent** — so login would work once and then silent-refresh would fail. Cross-site cookies
must be `SameSite=None; Secure`.

The fix (in production use `none`, locally keep `strict`):

```ts
const getCookieOptions = () => {
  const isProd = process.env.NODE_ENV === 'production';
  return {
    httpOnly: true,
    secure: isProd,                                   // required by SameSite=None; Render is HTTPS
    sameSite: (isProd ? 'none' : 'strict') as const,  // cross-site cookie in prod
    maxAge: 7 * 24 * 60 * 60 * 1000,                  // 7 days
  };
};
```

> This is the only code change needed for the split-origin deployment.

## Part 1 — MongoDB Atlas (produces your `MONGO_URI`)

1. Go to **mongodb.com/cloud/atlas** and sign up (free).
2. **Create a cluster** → choose **M0 (Free)**. Pick a provider/region close to your Render
   region (Render free: US / Frankfurt / Singapore — pick the nearest). Name it `Cluster0`.
3. **Database Access** → **Add New Database User** → *Password* auth. Username `opticart_user`,
   generate/set a password and **save it**. Role: *Read and write to any database*.
4. **Network Access** → **Add IP Address** → **Allow Access from Anywhere** (`0.0.0.0/0`).
   Required — Render free has no fixed outbound IP to whitelist.
5. **Clusters → Connect → Drivers → Node.js** and copy the string:
   ```
   mongodb+srv://opticart_user:<db_password>@cluster0.ab1cd.mongodb.net/?retryWrites=true&w=majority&appName=Cluster0
   ```
6. Turn it into your final **`MONGO_URI`**: replace `<db_password>` with the real password and
   insert the database name `opticart` before the `?`:
   ```
   mongodb+srv://opticart_user:YOURPASS@cluster0.ab1cd.mongodb.net/opticart?retryWrites=true&w=majority&appName=Cluster0
   ```
   > If the password contains `@ : / ? # % &`, URL-encode it (`@` → `%40`). Easiest to use an
   > autogenerated alphanumeric password to avoid this entirely.

## Part 3 — Deploy the API (Render **Web Service**)

**New + → Web Service →** connect the repo, then:

| Field | Value |
|---|---|
| Root Directory | `server` |
| Runtime | Node |
| Build Command | `npm install --include=dev && npm run build` |
| Start Command | `npm start` |
| Instance Type | **Free** |

> `--include=dev` is required: TypeScript/tsx are devDependencies, and with
> `NODE_ENV=production` set, a plain `npm install` skips them and the build fails.

**Environment variables:**

| Key | Value |
|---|---|
| `MONGO_URI` | your Atlas string from Part 1 |
| `JWT_ACCESS_SECRET` | a long random string (below) |
| `NODE_ENV` | `production` |
| `CLIENT_URL` | leave blank for now — set in Part 5 |

Generate a secret: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`

**Do NOT set `PORT`** — Render provides it; `server.ts` already reads `process.env.PORT`.

Optional (otherwise the app runs in safe mock mode): `STRIPE_SECRET_KEY`,
`STRIPE_WEBHOOK_SECRET`, `CLOUDINARY_URL`, `GMAIL_USER`,
`GMAIL_APP_PASSWORD`.

Create the service. When live, note the URL (e.g. `https://opticart-api.onrender.com`) and
test: `https://opticart-api.onrender.com/api/health` → `{"status":"OK", ...}`.

## Part 4 — Deploy the client (Render **Static Site**)

**New + → Static Site →** same repo, then:

| Field | Value |
|---|---|
| Root Directory | `client` |
| Build Command | `npm install && npm run build` |
| Publish Directory | `dist` |

**Environment variables:**

| Key | Value |
|---|---|
| `VITE_API_URL` | `https://opticart-api.onrender.com/api` |

> Note the trailing **`/api`** — `client/src/services/api.ts` expects it. Vite bakes this in
> **at build time**, so if you change it later, redeploy the client.
> Optional: `VITE_STRIPE_PUBLISHABLE_KEY`.

**SPA rewrite (important for React Router):** service → **Redirects/Rewrites** → Add →
Source `/*`, Destination `/index.html`, Action **Rewrite**. Without this, refreshing on a
route like `/products` returns 404.

Create the site. Note its URL (e.g. `https://opticart-client.onrender.com`).

---

## Part 5 — Connect the two (CORS)

API service → **Environment** → set:

```
CLIENT_URL = https://opticart-client.onrender.com
```

Save (triggers a redeploy). Now `server.ts` allows the client origin with credentials.
This, plus the cookie fix, is what makes login work.

---

## Part 6 — Seed the database (one time)

Atlas starts empty. Seed it from your own machine, pointed at Atlas:

1. In `server/.env` locally, set `MONGO_URI=` to the Atlas string.
2. From the `server` folder: `npm run seed`

Creates demo accounts:

| Role | Email | Password |
|---|---|---|
| Customer | `customer@opticart.dev` | `Customer123!` |
| Manager | `manager@opticart.dev` | `Manager123!` |
| Admin | `admin@opticart.dev` | `Admin123!` |

Set your local `MONGO_URI` back to localhost afterward if you keep developing.

---

## Part 7 — Verify

Open the client URL, log in with a seeded account, navigate, and **refresh the page**. If you
stay logged in, the cookie fix + CORS are correct.

## Troubleshooting

### Client build fails: `Cannot find native binding` / `@rolldown/binding-linux-x64-gnu`
Vite 8 uses Rolldown, which ships **platform-specific native binaries**. Two things
combine to break the Linux build:

1. **The lockfile is the root one, not the client one.** This is an npm **workspaces**
   repo, so even when the build runs inside `client/`, npm walks up and uses the
   **root `package-lock.json`**. A root lockfile generated on Windows triggers npm's
   optional-dependency bug (npm/cli#4828) and the Linux binary is skipped.
2. **Render caches `node_modules`.** A build log line like `up to date … in 1s` means the
   cached (broken) `node_modules` was reused, so the binary never gets reinstalled.

**Fix:** delete the tracked **root `package-lock.json`** and push, then on the client
service do **Manual Deploy → Clear build cache & deploy**. With no lockfile and a cleared
cache, npm resolves fresh on Linux and installs the correct binary. (You are on Windows, so
a committed lockfile will always pin Windows binaries — leaving it out is the pragmatic fix.
`server/package-lock.json` can stay; the server has no native dependencies.)

### API build fails: `tsc` type errors
Make sure you've pushed the production-build fixes (the `MONGO_URI` fallback in
`server/src/config/db.ts` and the cross-site cookie in `auth.ts`). Render runs
`npm run build` (`tsc`), which type-checks — unlike local `tsx` dev, which does not.

## Free-tier notes

- **API cold starts:** Render free web services sleep after ~15 min idle; the next request
  takes ~50 s to wake. First login after a break feels slow — normal. Optionally keep it warm
  with a free uptime pinger hitting `/api/health`.
- **Atlas M0:** 512 MB shared storage — plenty for this demo.
- **Order of operations:** deploy the API first so you know its URL before setting
  `VITE_API_URL` on the client.
- **Optional real services:** for live Stripe, set `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET`
  and point a Stripe webhook at `https://<api>/api/orders/webhook`. For real image uploads, set
  a real `CLOUDINARY_URL`. Without these, the app uses safe mock behavior.
